# godsh v0.7.0

godsh — DeepSeek Harness 的图形化环境配置启动器与电影级控制中心（双模主题 · 动态极光 · 无控制台启动）。

> **这一版是形态上的跃迁：godsh 第一次真正住进了 dsh 里面。**
> 它不再只是"在 dsh 外面帮你把环境管好"的启动器 —— 它**本身成了一个 DSH 插件**：
> 在 dsh 的设置页里有自己的面板，宿主半跑在 dsh 进程内。
> 更重要的是，本项目一直挂在嘴边的那句话——**「不重启 dsh 就能重载插件」**——
> 这一版第一次被**实测证实**（而不是"应该能行"）。
> 同时修掉了你反馈的五项缺陷，其中三项的根因都不是"功能没做"，
> 而是**判据选错了字段**，或者**只改了容器却没管后代**。

## ✨ godsh 成为 dsh 内的插件：`@godsh/dsh`

新增双面插件包（宿主半 + 浏览器半）：

- **宿主半**跑在 dsh 进程内，**零外部依赖**（所有服务运行时惰取）。
  因此 `headless` / `sdk` 这类没有 web 服务器的 profile 也能正常装载，
  而不是"因为缺一个可选服务就干脆装不上"。
- **浏览器半**经 `settings.section` 注册一个真实的设置页。顺带纠正了一处历史错误：
  旧插件注册的 `workbench.sidebar.item` 与 `global.overlay` 这两个槽位
  **在整个 dsh 树里根本不存在** —— 所以那块界面从来没有渲染过。
- 装载契约三处齐备：`dsh.bundle.patch` + `cordis.patch.yml` +
  patch 行 id 与宿主半 `export const name` **逐字一致**。

**实测证据**（不是"应该能行"）：

| 检查 | 结果 |
|---|---|
| `dsh plugin add link:` 后是否进入 `dsh.profile.bundles` | ✅ 进入，且无「declares no bundle」告警 |
| `dsh --profile <p> --dump-config` 是否出现该行 | ✅ 出现 `- id: godsh` |
| 服务端返回的 boot 组合脚本里是否含浏览器半 | ✅ 含 `@godsh/dsh/client.js` |
| 真实浏览器里是否真的渲染出来 | ✅ 点开「设置」，侧栏出现**「godsh 插件沙箱」** |

## ⚡ 零重启热装载：从"设想"变成"实测通过"

宿主半实现了**热装载桥**：在插件自己的 `apply()` 里直接操作运行中的 Cordis loader
（`create` / `update` / `remove`），提供 `mount` / `setDisabled` / `unmount`。

**实测结果**：

| 观测 | 结果 |
|---|---|
| 客户端模块图条目数（基线 → 装载后） | **54 → 55**，且目标包名出现在图里 |
| 卸载后 | 回到 **54**，目标包名消失 |
| **dsh 进程 PID** | **全程未变**（没有重启） |
| 观测方式 | 每次重连取 SSE `graph` 快照再对比，**不靠截图**；脚本见 `scripts/exp/h1-hot-mount.mjs` |

### 也说一条负结论（如实记录）

dsh 自带的「监听 `cordis.patch.yml` 并整栈重放」这条通道，在本机 `0.1.5-rc.1` 上
**不生效**。我做了 6 次观测：

- 写入新 row 的 `insert` 行；
- 对**已存在** row 做 id 定向 `disabled: true`（这条不依赖包解析，因此能排除"其实是解析失败"）；
- 写入**非法 YAML**（若真有人监听，必然报错）；
- 写入方式分**原子替换**与**原地覆写**两种（排除"rename 把文件监视弄丢了"）；
- 启动带与不带 `--expose-internals`（该 flag 是 dsh HMR 服务的构造前置条件）。

**全部零可观测效果**：图无变化、dsh 输出零增长、进程存活。同时实测确认
`--expose-internals` 确实可用、SSE 通路是活的 —— 所以缺口既不在那个 flag 上，也不是探针瞎了。

这也是为什么本版走的是"我们自己在运行树里动手"而不是"写文件等 dsh 重放"：
前者可验证、可回滚，后者在本机根本不动。完整证据见仓库内
`09_输入文档/新文档/G0实验结论-活层装载通道.md`。

## 🩹 你反馈的五项缺陷，全部修完

### 1️⃣ 浅色模式下「黑色框里的字看不见」

**根因**：那段暗色容器样式**只改了容器自己**的背景与文字色。而 CSS 的 `color` 只沿**继承**往下传，
后代只要被显式改过颜色就会赢 —— 偏偏同一个浅色块里把 `.badge`、`.mono-tag`、表格单元格、
卡片标题的前景色都设回了深色。于是"深灰字压近黑底"。

**修法**：把「暗井」从两条 `!important` 升级为**令牌作用域** ——
井内在自身作用域重新定义中性色与语义色令牌，再对写死字面色的那几个后代做井内替换。
两条腿站住，不靠优先级硬压。

**顺带承认一件事**：我此前的对比度审计报告过"全部达标"，而你仍然看得见坏例。
所以这一版**先重写审计**：改成**逐文本节点**求解实际生效背景，
并强制带**阳性对照** —— 注入的已知坏例必须被报出来，**报不出来则整份结果作废**。

| | 修复前 | 修复后 |
|---|---|---|
| light 违规 | 2 条 | **0** |
| 暗井内注入复现 | **567** 例 | **0** |
| dark / 无主题 | 1 / 3 | **0 / 0** |
| 阳性对照 | — | 全部检出，9/9 页面覆盖 |

顺带修掉审计查出的 4 项井外遗留（`.dash-value` 1.88:1、`.drag-grip` 4.08:1、
基座 `--vault-2` 4.41:1、`badge.disabled` 深色 4.05:1）。

### 2️⃣ 「为什么必须先『分配』才能用」

你说得对：**启用态才是标准态**。而 `分配` 从来就不是一个业务动作 ——
它只是"把这一行写进 `cordis.patch.yml`"的唯一入口。安装流程只做了物理挂载，
从不写补丁层，于是插件处于"物理在、声明不在"，dsh 直接忽略它。

**修法**：安装/注入成功之后**自动写入分配并落地补丁层**，接入全部四个出口。
官方资产不纳管；**幂等**（之前被禁用过的会显式改回启用）；**绝不抛异常**
（一次成功的安装不能被"启用失败"改判成失败）。

前端语义一并改到说得通为止：未分配→**未启用**、分配→**启用**、移除分配→**禁用**、
全部分配→**全部启用**。

用 **7 例离线单测**钉住决策逻辑 —— 之所以要离线，是因为真实安装要走 `pnpm add`（联网），
而"点一次看看成不成"无法区分"判据错了"和"网络抖了"。

### 3️⃣ 「插件沙箱不能全部更新」

**根因是判据选错了字段**：更新器只认 `source !== 'local'`，
而**收割入库一律写 `source: 'local'`** —— 两者交集为空，
所以"全量更新"先天不可能更新任何收割来的插件。而沙箱里的绝大多数正是收割来的。

`source: 'market' | 'local'` 是个二值垃圾桶：它把「npm 装的」「git 装的」
「本地目录导入的」「从环境收割的」四类压成同一个 `local`，
而"能不能从 npm 更新"需要的恰恰是这四类的区分。

**修法**：引入**真实来源**模型与唯一判据；来源缺失时由纯函数推断，
**历史数据无需迁移**即可恢复可更新。另修掉一处"报告说谎"：全量更新原先无条件把
`updated` 加一并打印「升级成功」，即便底层返回失败。前端那个按钮也不再被
"有没有检测到更新"门控 —— 原门控会让它在最需要的时候消失。

### 4️⃣ 「在总环境里实现全部，而不是分类文件夹内实现」

新增**环境级**的「全部启用 / 全部禁用」，与原有的「全部更新」并列。
特别说明「全部禁用」的语义：它只把已有分配置为禁用，**不删除记录、不动 bundles** ——
所以禁用之后**环境仍然可以启动**。这是与"卸载"完全不同的两件事。

### 5️⃣ 「在所有地方都不要实现官方插件」

把散落在**四处**的官方包硬编码集合收敛成**唯一事实源**，判据从"枚举包名"
改成"作用域前缀" —— 官方将来新增或改名一个 bundle，这里都不需要改。
服务端统一给负载打上"是否官方"，前端零判定代码。
官方资产从"可分配 / 可更新 / 可卸载"清单里退场，改为一个**只读的**
「官方内核（由 dsh 维护）」面板。

## 🧹 另外修掉的

- **测试不再污染仓库的数据目录**：`PatchManager` 的备份目录取自模块级常量，
  测试无法用环境变量覆盖，于是每轮测试都往仓库 `data/patches-backup/` 写文件
  （实测已累积 126 个）。现改为可注入（生产行为不变），跑一轮后文件数 **126 → 126**。
- **补记 0.6.5 的一处加固**（当时漏写进说明）：安装器选择原先会把 tauri 产物目录下
  **所有**历史安装器拷成同一个目标名，谁最后被枚举到谁就赢 ——
  顺序一变就会把上一版的安装包当成新版发布。现改为按版本号精确筛选，
  且候选数不为 1 就直接失败（**宁可发不出去，也不发错包**）。

## 🧭 这一版**没有**做（如实登记）

- **dsh 内的完整沙箱页**：目前给的是热装载桥 + 只读自检面板，
  还不是一个能在 dsh 里管沙箱的完整界面。
- **影子校验**（先在一个一次性实例里试跑，坏插件根本进不了你和 dsh 的对话）、
  **原生热重载后端**（因为上游那条通道在本机不生效）、
  **交接式重启**（进程换了但对话续上）—— 都未实现。
- 沙箱列表的「来源徽章」未做。
- 首启 dsh 实测约需 **70 秒**才打印认证地址（要等插件树结算完才打印），
  godsh 的启动等待预算是否够用**尚未复核**，已登记为已知风险。

## 升级建议

直接覆盖安装即可，环境与配置不受影响。这一版对**已存在的环境**只多做一件事：
在启动前用统一判据检查 `dsh.profile.bundles`，把"能解析但并非 bundle"的历史遗留条目
**报出来并给出可读原因**，而不是等 dsh 抛一句英文错误。
