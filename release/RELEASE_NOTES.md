# godsh v0.6.6

godsh — DeepSeek Harness 的图形化环境配置启动器与电影级控制中心（双模主题 · 动态极光 · 无控制台启动）。

> **这一版的主题是「地址未就绪 ≠ 网络问题」。**
> 「地址未就绪」这四个字，是 godsh 用户最常撞上、也最容易被误读的一句话：
> 它听起来像网络问题、像端口冲突、像 dsh 没装好，
> 于是大家去查代理、换端口、重装 dsh——**全都无效**。
> 真正的原因，是 `~/.dsh` 里一枚**几十字节的孤儿锁文件**。
> 这一版把它连根拔掉：**启动前自动清理孤儿凭据写锁**，
> 并把这条因果链写进诊断里，让「地址未就绪」第一次有了可执行的解释。

## 🩹 一个被误读的故障现象：删掉一个锁文件就好了

**现象**：启动环境时，界面只显示一句「**地址未就绪**」，除此之外什么都没有。
用户完全看不出原因——而这四个字会把人引向完全错误的方向：
以为网络不通、以为端口被占、以为 dsh 装坏了。
**唯一的自救线索是**：手动删掉 `~/.dsh/.credentials.yaml.lock` 之后，一切恢复正常。

**根因（实测定位，证据链完整）**：

1. dsh 的 `@deepseek-ai/dsh-atomic-write` 用 `wx` 创建 `<文件>.lock` **兄弟锁**，
   文件名就是 `xxx.lock`，**内容就是持有者的 PID**；
2. `@deepseek-ai/dsh-client-connection` 在**插件树加载期**就要写 `.credentials.yaml`——
   也就是说，**锁不是「用到凭据时才出现」，而是启动早期就出现**；
3. 因此**任何一次启动期崩溃、或被强杀**（例如安装/升级时结束进程、任务管理器结束进程），
   都会把这枚锁留在磁盘上；
4. 残留锁让**下一次**启动在 `boot()` 里抛
   `atomic-write: timed out waiting for the writer lock`（默认只等 **2000ms**）
   → `plugin tree failed to load`
   → 进程**在打印 `dsh web: …?token=…` 之前就已经退出**；
5. godsh 靠解析那行地址拿到认证 URL，进程没打印，于是**抓不到地址** → 界面显示「地址未就绪」。
6. 上游**刻意不自动回收**这枚锁——它的注释写明：**文件年龄无法证明持有者已经死了，
   孤儿锁的回收属于 operator action（人工操作）**。

**修法**：godsh 就是那个 operator。`dsh-heal` 新增四个导出函数：

| 函数 | 职责 |
|---|---|
| `readLockHolderPid` | 读出锁文件第一行里的持有者 PID（读不出数字返回 `null`） |
| `isProcessAlive` | `process.kill(pid, 0)` 做存在性探测；**只有 `ESRCH` 才判定已死**，`EPERM` 一律当作存活 |
| `clearOrphanCredentialLock` | 保守清理：真孤儿才删，并分别返回 `removed` / `kept` / `unknown` |
| `diagnoseCredentialLock` | 供 `diagnoseProfile` 报出，**把「PID 已不存在」与「表现为地址未就绪」明确对应** |

- 接入**启动前自愈**：`healDepTreeForStart` 现在同时负责「依赖树垫片」与「孤儿锁清理」，
  **每次启动都跑**（启动与重启两条路径的 4 处接线全部覆盖），**幂等**；
- **判据刻意保守**——宁可不清，也不误删别人正在持有的锁：
  - 读出 PID 且**进程已不存在** → **删**（真孤儿）；
  - 读出 PID 且**进程仍存活** → **留**（真的有人在写）；
  - **读不出 PID / 文件为空** → **留**（无法证明是孤儿）并交给诊断层报出；
- 清理失败**绝不阻断启动**，诊断层下次继续报。

## ⚠️ 已知限制 / 边界

以下都是**明确边界**，不是「还没做」：

- **⚠️ 重装全局 dsh 换不来根治（本版最重要的实测结论）。**
  实测把 godsh 的兼容垫片产物（`negotiator/node_modules/content-type`）**移开**后，
  dsh 实例仍在**首个带 `Accept-Encoding` 的请求**上死亡（`TypeError: invalid media type`）——
  说明**上游依赖清单本身不自洽**：顶层 `content-type@1.0.5` 与 `negotiator@1.1.0` 要求的 `^2.1.0` 冲突。
  因此 godsh 的**启动期垫片是承重的正式对策**（不是权宜之计），**请勿移除**；
  换 dsh 版本、重装全局包都无法替代它。
- **只清理「能证明是孤儿」的锁**：锁里 PID 仍存活、或文件内容读不出数字时，
  godsh **不会**删（宁可留着），只在诊断里报出并建议人工确认。这是刻意的保守——
  误删一把活锁比留一把死锁危险得多。
- **清理发生在「godsh 启动环境之前」**，不是实时巡检：
  若 dsh 在**运行中**崩溃并留下锁，需要下一次启动（或手动点一次启动/诊断）才会被清掉。
- **PID 复用理论上存在**：极端情况下锁里的 PID 可能被系统回收给另一个无关进程，
  此时 godsh 会判定「持有者存活」而保留锁（保守方向的误判），表现为不清理 + 诊断报告，需人工介入。
- **本轮只修「地址未就绪」的一条因果链**：界面若仍显示该文案，可能是其他原因
  （dsh 未安装、环境损坏、真实网络/端口问题等），请以「诊断」页的结论为准，而不是只看这一句话。
- **上游垫片仍受「有无合规来源」限制**：若本机确实不存在任何合规的 `content-type` 副本，
  垫片不会从网络下载，诊断会给出 CRITICAL 并说明原因，需要人工介入。
