## 三、核心体系一：仓库沙箱中枢（Plugin Vault）彻底替代 pluginsbag

### 3.1 痛点反思：为什么自建 Profile 暂存是架构反模式？

在之前的实际使用中，用户创建了一个名为 `pluginsbag`（或 `plugin_bag`）的 Profile 来放插件，这带来了难以根治的技术债：
1. **庞大的磁盘污染**：`pluginsbag` 本身是一个 Profile，每装一个插件都会在自己的 `node_modules` 下生成冗余依赖，动辄吃掉数 GB 磁盘。
2. **迁移阻抗极高**：要把 `pluginsbag` 里的插件给 `web`，必须执行 `move-with-install`，后端需要重新调 `dsh plugin add`，重新跑 pnpm 解析，经常耗费 1~2 分钟甚至网络中断。
3. **环境混淆与误启动**：在环境列表里经常容易误点启动 `pluginsbag`，造成端口浪费或进程冲突。
4. **无法承载本地未发布插件**：自己写的插件或 GitHub 下载的源码，无法直接丢进 Profile 里被识别。

---

### 3.2 沙箱底层存储模型：全局 CAS 池与 NTFS Junction 软链

我们在 `%APPDATA%\godsh\` 下设立专用的资产中枢：
```text
%APPDATA%\godsh\
  ├─ data/
  │   ├─ vault.json            # 插件元数据库（名称、版本、分类、来源、契约要求）
  │   └─ presets.json          # 套件预设库（如“AI编程套件”、“学术套件”）
  └─ vault_store/              # 内容寻址存储池 (Content-Addressable Pool)
      ├─ dsh-web-search-pro@0.1.11/
      ├─ @anweat/dsh-browser@0.1.10/
      ├─ dsh-task-panel@latest/
      └─ local-my-agent-tools/ # 本地导入插件源码或解压包
```

#### 零开销秒级注入原理
当用户在 GUI 界面将沙箱中的插件拖入/点选到 `web` 或 `dshcoding` 时：
1. **不走网络，不跑漫长的 pnpm install**；
2. 系统在目标 Profile 的 `node_modules` 目录下直接创建 **NTFS Directory Junction（目录连接点）**，指向 `vault_store` 中的对应插件包；
3. 将包名与版本以原子操作追加到目标 Profile 的 `package.json` 与 `cordis.patch.yml`；
4. **分配耗时从原来的 60 秒降至 100 毫秒以内**！真正实现丝滑流转。

### 3.3 “就绪态（Migration-Ready）”的四阶流转生命周期

```text
[阶段 1: 录入] ──> [阶段 2: 预检审计] ──> [阶段 3: 就绪态 (Staged)] ──> [阶段 4: 瞬时分发]
 市场点选暂存      解包 package.json       常驻沙箱卡片流              拖拽/点击指定 Profile
 本地文件导入      提取 Cordis 依赖契约    分类徽标/版本标记           0耗时 Junction 软链
 Git 地址直连      allowBuilds 规则就绪    开机静默版本比对           patch 原子写回
```

- **就绪态特征**：插件已经处于“解压完成、依赖就绪、格式合法、服务契约清晰”的状态。
- **分类管理**：沙箱支持 dshmarket 官方 22 分类（agi, ui, tools, workflow, dev 等），并允许用户自定义标签（如“核心常用”、“自研调试”）。
- **完全删除与级联管理**：在沙箱中删除插件时，可选择：
  - **仅从沙箱移除**：不破坏已使用该插件的环境；
  - **全域强力清理（Cascade Uninstall）**：扫描所有 Profile，一并移除分配并清除软链接，保持环境整洁。

### 3.4 本地插件全格式导入引擎（tgz、zip、源码文件夹、Git直连）

针对插件开发与离线插件安装，GUI 端打造专属 **“📥 导入中心”**：

#### 1. 导入源全格式覆盖
- **`.tgz` 文件**：npm pack 生成的标准发布包，自动解压至沙箱；
- **`.zip` 压缩包**：GitHub 归档或离线分享包，自动寻找到包含 `package.json` 的子目录并提取；
- **本地源码文件夹（开发模式）**：
  - 直接将本地开发路径以符号链接方式挂载入沙箱；
  - **新增「联动热重载」开关**：开发者在 VSCode 里修改本地插件代码，沙箱与已分配的 Profile **实时生效**，免去反复打包安装的痛苦！
- **Git 仓库 URL**：输入 GitHub/Gitee 仓库地址，后端轻量执行 `git clone --depth=1` 直接拉入沙箱。

#### 2. 本地插件导入预检与自愈管线
在插件入库前，沙箱引擎自动完成 4 步体检：
1. **格式验证**：检查是否具备合法的 `package.json`，缺失时引导用户界面输入插件名与版本；
2. **类型识别**：自动分析 `cordis.service` 或 `dsh.profile.bundles`，判定是 Bundle 插件还是 Client 插件；
3. **伴随依赖提取**：检查该插件是否需要 peer 依赖（如 `browser`、`database` 等），一并记录在沙箱契约中；
4. **编译预处理**：若检测到未编译的 TypeScript 源码或需要原生编译的包，沙箱提前在后台触发构建，避免分配到环境时编译失败。

### 3.5 启动静默差量检更与“防文件锁撕裂”热升级机制

#### 1. 启动异步无感检更
- 启动 GUI 客户端时，主线程优先加载本地 UI 与状态（50ms 呈现）；
- **3 秒后后台静默 Worker 启动**：
  - 读取沙箱内所有非 local 插件的最新版本；
  - 采用 HTTP/2 并发批量查询国内极速源 `https://registry.npmmirror.com`，每个包仅查询轻量元数据，全量检更在 1 秒内静默结束；
  - 若有更新，沙箱图标显示红点徽标 `New (3)`，展开可看到每个插件的具体升级说明。

#### 2. 防 Windows 文件锁撕裂机制（针对运行中环境的升级）
- **痛点**：如果 Profile 正在运行，直接更新插件文件会被 Windows 锁定（`EPERM: operation not permitted`），或者导致运行中的服务读取到半新半旧的文件而崩溃。
- **创新解法 —— 版本槽位双重缓冲（Version Slot Buffering）**：
  1. 沙箱将新版本下载到独立版本目录（例如从 `v1.0.0` 升级到 `v1.1.0`，存储在 `vault_store/pkg@1.1.0`）；
  2. 当前正在运行的环境不受任何影响，继续读 `pkg@1.0.0`；
  3. 在 GUI 卡片上打上 **「待重启生效」** 徽标；
  4. 下次环境重启时，秒级切换 Junction 指针到新版本。**彻底终结 Windows 下的文件占用报错！**

### 3.6 插件深视镜（Inspector）与套件预设包（Preset Bundles）

- **插件深视镜（Inspector）**：
  - 在沙箱中选中任意插件，右侧抽屉展现该插件的：
    - 运行依赖图谱与 Cordis 契约；
    - 当前有哪些 Profile 正在使用它（反向索引）；
    - 本地磁盘占用大小；
    - 快速测试与配置项编辑。
- **套件预设包（Preset Bundles）**：
  - 允许将一组常用插件保存为一个“组合包”（例如「AI 编程全家桶」、「日常办公套件」）；
  - 新建环境时，无需一个个挑插件，选择套件即可**一键打包分发**。

### 4.1 用户端安全（User Protection）：审计时光机与误伤阻断
1. **高危操作防误触**：
   - 删除环境、重置沙箱、清空全局数据等操作，在弹窗中必须**手动输入目标对象全名**方可激活确认按钮；
   - 运行中的环境严格禁用删除操作，并在悬停时给出明确 Tooltip：“请先停止环境”。
2. **分配时光机（Allocation Rollback Engine）**：
   - 每次对插件的增删改、拖拽移动，系统在 `data/snapshots/` 自动生成时间戳快照；
   - 顶部工具栏常驻「↩ 撤销」按钮。如果配置改乱导致服务异常，点击撤销即可在 1 秒内回滚配置文件。

### 4.2 DSH 核心端安全（Core Protection）：配置写锁与哨兵进程
1. **官方内核基座免死金牌**：
   - 核心依赖 `@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app` 在 GUI 前端直接**隐藏删除按钮**；
   - 后端路由在处理卸载或重排请求时进行拦截，确保无论用户如何拖拽，基础 Web 运行基座永远存在。
2. **YAML Patch 原子写回与防空补全**：
   - 序列化器重构：若检测到分配列表为空，绝对禁止写出 0 字节文件，强制输出标准 `[]\n`；
   - 写入采用原子写入法：先写临时文件 `.cordis.patch.yml.tmp`，写入校验合法后再执行原子替换（Rename），防止意外断电或程序崩溃导致文件损坏。
3. **孤儿进程清理哨兵**：
   - 启动前自动调用 `netstat` 与 Windows WMI 接口，检测目标目录与端口是否被历史残留的孤儿 `node.exe` 进程占锁；
   - 若发现占用，自动提示并提供一键清理释放。

### 4.3 插件端安全（Plugin Protection）：伴随依赖契约图与编译沙箱
1. **服务契约自愈网络（彻底终结 Bug 2）**：
   - 建立内部 Service 注册表，明确常见功能插件的底层提供者：
     ```typescript
     export const SERVICE_CONTRACTS = {
       'dsh-web-search-pro': { requires: 'browser', providedBy: '@anweat/dsh-browser' },
     ```

## 五、核心体系三：动态随机端口与统一反向代理网关引擎

### 5.1 动态端口分配带来的真实痛点：书签失效与记忆负担

用户提出了极好的思路：*“每一次打开的时候如果没有用户自定义，能不能随机端口数字（在该端口没有被占用的情况下）？”*

**深入思考其工程落地难点**：
- 如果每次启动都完全随机（如今天 3412，明天 3891），用户在浏览器中保存的书签将全部失效，无法记住地址，甚至桌面端 WebView 也需要频繁寻找目标端口。

### 5.2 解决方案：动态安全端口协商算法 + 统一反向代理网关

我们设计了一套兼具**“完全免冲突”**与**“固定入口统一访问”**的进阶架构：

```text

               │    统一反向代理网关 (godsh 主服务 127.0.0.1:4780)│
               └──────────────────────┬───────────────────────┘

                 ┌────────────────────┴────────────────────┐
                 ▼                                         ▼
   http://127.0.0.1:4780/app/web/            http://127.0.0.1:4780/app/dshcoding/
                 │                                         │
                 ▼ (内部反向代理，用户无感知)                ▼ (内部反向代理，用户无感知)

   (每次启动自动避让占用随机分配)               (每次启动自动避让占用随机分配)
```

#### 1. 动态安全端口协商引擎 (`resolveSafePort`)
- 用户有自定义端口且未被占用时：优先使用用户设定的固定端口；
- 用户未自定义（或端口发生冲突）时：在安全私有端口区间 `3200~3999` 内自动执行双重探活并随机分配一个空闲端口。

```typescript
// packages/core/src/port-engine.ts
import net from 'node:net'
import { findPidByPort } from './process-manager.js'

export async function isPortAvailable(port: number, host = '127.0.0.1'): Promise<boolean> {
  // 1. 系统底层 netstat 进程探活
  if (findPidByPort(port) !== null) return false

  // 2. 原生 Socket 端口独占性监听测试
  return new Promise((resolve) => {
    const s = net.createServer()
    s.unref()
    s.on('error', () => resolve(false))
    s.listen({ port, host, exclusive: true }, () => {
      s.close(() => resolve(true))
    })
  })
}

export async function resolveSafePort(
  preferredPort?: number,
  range: [number, number] = [3200, 3999]
): Promise<number> {
  if (preferredPort && preferredPort > 0) {
    if (await isPortAvailable(preferredPort)) return preferredPort
  }
  const [min, max] = range
  for (let i = 0; i < 30; i++) {
    const candidate = Math.floor(Math.random() * (max - min + 1)) + min
    if (await isPortAvailable(candidate)) return candidate
  }
  // 极端备用：由操作系统内核自动指派
  return new Promise((resolve, reject) => {
    const s = net.createServer()
    s.listen(0, '127.0.0.1', () => {
      const port = (s.address() as net.AddressInfo).port
      s.close(() => resolve(port))
    })
  })
}
```

#### 2. 统一反向代理网关（可选旗舰特性）
- godsh 后端内置轻量 HTTP/WebSocket 反向代理：
  - 访问 `http://127.0.0.1:4780/app/<profile_name>/`，网关自动将请求反向代理到该环境实际运行的随机端口上；
  - **用户收益**：用户永远只需要收藏一个地址（如 `4780/app/web/`），无论内部 DSH 随机到了几千号端口，均能秒级打开，完美化解随机端口的寻址麻烦！
  - 界面卡片上同时显示直连端口（如 `:3214`）与网关入口，双通道均可访问。

### 2. 后端核心路由接口 (`apps/launcher/src/routes/vault.ts`)

```typescript
import type { ApiHandler } from './types.js'

export const vaultHandler: ApiHandler = async (ctx, req, res, method, seg, body) => {
  // GET /api/vault - 获取沙箱全量插件与就绪态信息
  if (seg.length === 1 && seg[0] === 'vault' && method === 'GET') {
    const list = ctx.vaultManager.listAll()
    ctx.sendJson(res, 200, { plugins: list, count: list.length })
    return true
  }

  // POST /api/vault/import-local - 导入本地插件包或目录
  if (seg.length === 2 && seg[0] === 'vault' && seg[1] === 'import-local' && method === 'POST') {
    const { targetPath, category, watchMode } = body
    const result = await ctx.vaultManager.importLocal(targetPath, { category, watchMode })
    ctx.sendJson(res, 200, result)
    return true
  }

  // POST /api/vault/deploy - 毫秒级分发沙箱插件到指定 Profile (Junction 软链 + 伴随自愈)
  if (seg.length === 2 && seg[0] === 'vault' && seg[1] === 'deploy' && method === 'POST') {
    const { targetProfile, pluginIds } = body
    const report = await ctx.vaultManager.deployToProfile(targetProfile, pluginIds)
    ctx.sendJson(res, 200, report)
    return true
  }

  // POST /api/vault/check-updates - 静默批量检更
  if (seg.length === 2 && seg[0] === 'vault' && seg[1] === 'check-updates' && method === 'POST') {
    const updates = await ctx.vaultManager.checkAllUpdates()
    ctx.sendJson(res, 200, updates)
    return true
  }

  return false
}
```

## 九、总结

4. 深度评选并给出了 **`dsh-task-panel` + `dsh-task-graph` 自动化编程套件**，让您的 DSH Web 客户端真正具备自主分解任务、多阶段自动推进开发的强大生产力。
