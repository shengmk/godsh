# godsh 改进建议（v0.2.2 基线）

> 基于对 v0.2.2 代码的完整学习（`docs/iteration-log.md`、`优化方案大纲.md`、`改进点（功能与界面）.md`）与实测（冒烟 17/17 + 打包运行）整理。
> 按「收益/成本」排序，标注优先级与预估工作量。

---

## A. 工程健壮性（建议优先，成本低、收益高）

### A1. 🔴 修复 bump-version.ps1 的 BOM 隐患（已触发过）
- **问题**：`bump-version.ps1` 用 `Set-Content -Encoding UTF8` 写回 JSON/Cargo 文件，Windows PowerShell 下会写入 **UTF-8 BOM**；tauri.conf.json 带 BOM 会被 serde_json 解析失败（历史迭代踩过），package.json 带 BOM 个别工具会告警。
- **本次已做**：
  - `bump-version.ps1` 修复根 package.json 的 `Get-Item` 空引用 bug；
  - 改为 `Write-NoBom`（`UTF8Encoding($false)`）写回 + 末尾无 BOM 校验；
  - 新增同步 `packages/core/src/config-store.ts` 的 `DEFAULT_CONFIG.launcher.version`（此前 bump 会漏掉，导致 health 返回旧版本号）；
  - 升级 0.2.2 后已全量去 BOM。
- **建议**：后续版本升级统一走 `bump-version.ps1`（已含校验），不要在脚本外手改版本号。

### A1b. 🔴 launcher 版本号不应被用户配置覆盖（已修复）
- **问题**：`readConfig()` 用 `...cfg.launcher` 合并，用户数据目录（`%APPDATA%\godsh\data\config.json`）里残留的旧版本号会覆盖应用内置版本 → 升级安装后 `/api/health` 仍显示旧版本（实测 0.2.1）。
- **本次已做**：`config-store.ts` 的 `readConfig` 中 launcher 仅合并 `name`，版本号永远取 `DEFAULT_CONFIG`（应用元数据与用户配置分离）。
- **建议**：后续升级版本时确认 health 返回新版本号（冒烟含此断言）。

### A2. 🔴 CORS 收紧 + 安全响应头
- **现状**：`server.ts` 所有响应 `Access-Control-Allow-Origin: *`（同源 Web/桌面场景不需要跨域开放）。
- **建议**：改为「同源时不发 CORS 头，仅在显式配置的 `launcher.allowedOrigins` 白名单时放行」；`sendJson` 统一加 `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store`（API 响应）。
- **工作量**：~1 小时。

### A3. 🟡 后端单元测试补全
- **现状**：功能靠冒烟脚本（`_smoke*.ps1`）验证，无自动化单测。
- **建议**：优先补 `patch.ts`（解析/序列化往返）、`allocation-manager`（分配/移动/去重/applyProfile 保留用户条目）、`unified-kernel`（幂等注入/还原）、`config-store`（读写/兜底）。用 `node:test`（零依赖，Node 20+ 内置）。
- **工作量**：~半天。

### A4. 🟡 Git 仓库初始化 + GitHub Actions 自动打包
- **现状**：项目尚未 `git init`，发布靠本地 `make-release.ps1`。
- **建议**：`git init` 首次提交；GitHub Actions workflow：push tag `v*` → 安装 Rust(mingw)/Node → `make-release.ps1` → 上传 `release/` 产物到 Release。
- **工作量**：~2 小时（含 Actions 调试）。

## B. 性能优化（延续《提示词.md》第三项）

### B1. 🟡 Profile 懒加载（启动只读目录名）
- **现状**：`/api/profiles` 每次 `scanProfiles` 全量读每个 Profile 的 package.json + cordis.patch.yml；前端 3s 轮询虽已改合并接口，但首屏与刷新仍全量扫描。
- **建议**：`GET /api/profiles/names` 只 `readdirSync` 返回名称列表；卡片先渲染名称+状态，展开/点击时再拉详情（`/api/profiles/:name`）；运行状态继续走合并轮询。
- **工作量**：~2 小时。

### B2. 🟡 日志轮询改 SSE 流式
- **现状**：环境页/内核日志每 2s 轮询 `/log` 拉全文。
- **建议**：`GET /api/profiles/:name/log/stream`（SSE，尾随文件增量推送）；前端 `EventSource` 替换轮询，请求数趋近 0。
- **工作量**：~3 小时。

### B3. 🟢 市场列表虚拟滚动
- **现状**：市场页 `plugins.slice(0, 200)` 截断 + 全量渲染。
- **建议**：引入 `react-window` 或自写容器化列表（固定行高 + 可视区裁剪），去掉 200 截断，支持全量浏览。
- **工作量**：~2 小时。

### B4. 🟢 5 个小 JSON 合并 state.json（高风险，建议独立迭代）
- **现状**：config/kernels/allocations/unified-kernel/dsh-envs 5 个文件分开读写。
- **建议**：仅在「多文件读写确为瓶颈」时做；需兼容迁移（读旧文件 → 写 state.json → 原子写 + 备份旧文件），并全量回归。**不推荐**与功能迭代混做。

## C. 功能完善（按用户价值排序）

### C1. 🔴 统一内核「按环境单独开关」
- **现状**：统一内核全局开关（开=应用到全部 Profile）。
- **建议**：允许在环境页/分配页对单个 Profile 覆盖（启用/跳过），满足「某些环境不想被注入 web-app 或用户插件」的场景；后端 `unified-kernel.json.managed` 已具备按环境记录的基础。
- **工作量**：~2 小时。

### C2. 🟡 环境批量操作（启停）
- **现状**：环境页已支持批量删除，但启停只能逐个点。
- **建议**：勾选后工具栏出现「批量启动/批量停止」，复用现有 `start/stop` 接口串行执行并汇总结果。
- **工作量**：~1 小时。

### C3. 🟡 端口占用可视化
- **现状**：启动失败提示「端口被占用」但看不到谁占着。
- **建议**：`GET /api/ports` 汇总当前运行端口 + 冲突检测（`findPidByPort` 已有）；失败诊断卡直接展示占用进程名/PID。
- **工作量**：~2 小时。

### C4. 🟡 Tauri 托盘 + 系统通知
- **现状**：桌面壳只有窗口。
- **建议**：托盘菜单（显示/隐藏、快速启动默认环境、退出）；环境启动完成/失败时系统通知。
- **工作量**：~半天（需 Rust 侧）。

### C5. 🟢 内容级 i18n（市场卡片等深水区文案）
- **现状**：i18n 覆盖导航/页头/设置，市场描述等动态内容仍硬编码中文优先。
- **建议**：市场描述按当前语言切换（zh/en 字段已有）；Toast 文案逐步抽到语言包。
- **工作量**：~半天。

### C6. 🟢 数据备份增强
- **现状**：设置页可导出/导入 JSON。
- **建议**：增加「定时自动备份」（每次启动前复制 data/ 到 data/backups/，保留最近 N 份）、备份文件一键打开目录。
- **工作量**：~1 小时。
